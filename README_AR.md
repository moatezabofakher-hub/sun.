# SAN SHINE — مشروع أندرويد آمن مع مولّد تراخيص منفصل

تم إعداد ملفين **منفصلين تماماً**:

1. **SAN-SHINE-GitHub-Public-Secure.zip**: مشروع Android كامل. هذا وحده هو الذي ترفع محتوياته إلى مستودع GitHub.
2. **SAN-SHINE-OWNER-PRIVATE-Generator.zip**: مولّد التفعيل الخاص بك ويحتوي على المفتاح الخاص RSA-3072. **احتفظ به خارج GitHub، ولا تشاركه مع العملاء**.

## إنشاء APK باستخدام GitHub فقط

1. فك ضغط ملف **GitHub-Public-Secure.zip**.
2. ارفع **كل محتويات المشروع** إلى جذر مستودع GitHub، بما فيها `.github/workflows/build-apk.yml` (لا ترفع ZIP وحده).
3. انتقل إلى **Actions → Build SAN SHINE Android APK → Run workflow**.
4. بعد نجاح العمل، افتح **Artifacts → SAN-SHINE-Android-APK**، ونزّل ملف ZIP الذي يحتوي على `app-debug.apk`.
5. هذا ملف **debug APK** للتثبيت والاختبار، وليس إصداراً موقّعاً للنشر على متجر Google Play. للنشر الرسمي يلزم مفتاح توقيع إصدار ونظام إدارة نسخ.

## الترخيص — طريقة آمنة من دون خادم

- يرسل العميل إليك **معرّف الجهاز** الظاهر في قسم التفعيل (`RD-...`).
- على **جهاز الإدارة فقط**، افتح `owner_generator_offline.html` أو استخدم `issue_license.py` الموجود في *الملف الخاص المنفصل*.
- اختر `owner_private_key.pem` داخل المولّد، واكتب معرّف جهاز العميل، واضغط توليد. انسخ الرمز الطويل الذي يبدأ بـ `SS1.`.
- ينسخ العميل رمز التفعيل إلى خانة التفعيل في التطبيق ويضغط تحقق/تفعيل.
- التوقيع يُفحَص محلياً عبر **RSA-3072 + SHA-256** ومفتاح عام مضمن في APK، ولا يتطلب الإنترنت.
- المفتاح الخاص **لا يوجد في HTML الخاص بالعميل، ولا APK، ولا GitHub ZIP**.

### مولّد Python (بديل للمتصفح)

```bash
python -m pip install cryptography
python issue_license.py RD-XXXXXXXXXXXX --output client-license.txt
```

على الهاتف، يمكن تجربة ملف HTML الخاص بالإدارة عبر متصفح يدعم `crypto.subtle` للملفات المحلية. إن لم يدعم المتصفح ذلك، استخدم Python على الحاسوب أو Termux. **لا ترفع المفتاح الخاص إلى مواقع خارجية أو Colab**.

## مهم قبل الاستعمال

- لا ترفع أبداً ملف **OWNER-PRIVATE-Generator.zip** أو `owner_private_key.pem`، حتى لو كان المستودع خاصاً. من يمتلك المفتاح الخاص يستطيع إصدار تراخيص.
- المفتاح الخاص الموجود في ملف الإدارة الحالي مرتبط بالمفتاح العام المضمن في هذا الإصدار. إذا فُقد فلن تستطيع إصدار تراخيص جديدة لهذا الإصدار؛ احتفظ **بنسختين احتياطيتين مشفرتين** خارج GitHub.
- **الرموز القديمة ACT-xxxx لن تُقبل** بعد فصل النظام، حتى لو كانت مفعّلة سابقاً؛ يجب إعادة إصدار رموز SS1 للعملاء. يحتفظ التطبيق بمعرّف الجهاز الموجود سابقاً إذا بقيت بيانات التطبيق محفوظة.
- لا تعِد بكون منع الاختراق مطلقاً: مهاجم يستطيع تعديل APK أو استنساخ بيانات التطبيق. هذه الآلية تحمي **سرّ التوقيع** من كشفه في APK، ولا تُعَد منظومة ترخيص مضادة لكل أشكال التلاعب.
- نظام التجربة الحالي ما زال يسمح بـ **100 عملية** قبل تفعيل النسخة؛ لم يُلغَ شرط التجربة من التطبيق.
- البيانات الحسابية الموجودة تبقى مخزنة محلياً في IndexedDB تحت نفس اسم قاعدة البيانات والتطبيق، إذا ثُبّتت النسخة الجديدة فوق السابقة بنفس توقيع APK ومعرّف الحزمة. **خذ نسخة احتياطية قبل التحديث**، ولا تحذف التطبيق القديم قبل نسخ البيانات.
- البصمة في النسخة القديمة عولجت عبر `BiometricPrompt` الأصلي في مشروع أندرويد، مع كلمة مرور وسؤالَي أمان بديلة.
- لا يزال نظام الطباعة الحالي يعتمد على الجسور الموجودة (RawBT أو تطبيق طرف ثالث) ولم تتم إضافة خدمة مباشرة لطابعة Xprinter.
- البناء في GitHub Actions يحتاج إلى توفر حزم Android SDK واتصال Maven، ولا يمكن تأكيد نجاح بناء APK فعلي قبل تنفيذ Workflow في مستودعك.

## الفحوص التي يعملها GitHub تلقائياً

- سلامة الملفات والبنية، وعدم وجود مفاتيح خاصة داخل المشروع.
- `node --check` للكود JavaScript.
- فحوص الحسابات والجرد والتحويل.
- فحص قبول رمز صحيح وتغيير جزء من الرمز ورفض التوقيع المزور وتقييده بمعرّف الجهاز.
- تجميع Android `:app:assembleDebug`، وإرفاق سجل الأخطاء عند الإخفاق.

## تحديث المفتاح إذا تسرب

لا يمكن تعطيل المفتاح العام المضمّن عن بُعد (التطبيق Offline). عند تسرب المفتاح الخاص، يجب إنشاء زوج مفاتيح جديد، تحديث المفتاح العام في التطبيق، إعادة إنشاء APK، وإعادة إصدار تراخيص. لذلك احتفظ بالمفتاح الخاص في جهاز الإدارة فقط.
